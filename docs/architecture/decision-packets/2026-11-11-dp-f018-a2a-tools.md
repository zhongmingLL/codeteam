# DP-F018A2A: A2A tools + InvocationQueue.enqueue 拍板包

> 只给价值取舍、推荐、证据和“不拍的后果”。技术细节不要求 operator 选。
> A2A tools 走 pi extension tool → control socket → daemon；不是 MCP callback。

## 0. 一句话

v1 的四个 A2A tool 已经和 Clowder 的 `post_message` / `cross_post_message` /
`multi_mention` / `thread_context` 对齐到“一个 source message 进 InvocationQueue”
的骨架；但 idempotency key 命名、multi_mention 的 queue 形状、operator target
生命周期、cross-thread provenance、`kind` 字段这五个选择会直接影响工具契约，
需要 operator 拍。

## 1. 先看结论

| 决策 | 选项 | 推荐 | 影响面 | 不拍的后果 |
|---|---|---|---|---|
| DP-F018A2A-1 幂等 key 叫什么 | A=`clientMessageId` 统一；B=`requestId` 统一；C=tool 用 requestId、credential 用 clientMessageIds | **A** | tool input、credential map、queue payload、错误 taxonomy | 同一个 key 两个名字，实现和文档继续分叉 |
| DP-F018A2A-2 `multi_mention` queue 形状 | A=1 message + 1 queue entry + N targets；B=N messages/queue entries；C=1 message + N queue entries | **A** | fan-out 语义、credential claim、queue admission | queue 形状无法定稿，multi_mention 无法实现 |
| DP-F018A2A-3 operator target 生命周期 | A=只通知；message dispatchRef 同事务 settle；不建 parent/TurnExecution；B=建独立通知行；C=不支持 operator target | **A** | operator-only、mixed targets、read model | operator 通知和 agent 执行的生命周期混在一起 |
| DP-F018A2A-4 cross_post_message 边界 | A=同 user + target thread active/not deleted/projectPath + `extra.crossPost` provenance；B=只查同 user；C=允许跨 user | **A** | 跨 thread 可达性、审计、安全边界 | 跨 thread 的 access/provenance 无法定稿 |
| DP-F018A2A-5 `kind` 字段 | A=v1 删除；B=只进 `extra.presentation.kind`；C=保留 required | **A** | tool input、StoredMessage schema、UI | `kind` 继续和 legacy task-first 语义纠缠 |

### 1.1 已拍板（2026-11-11）

| 决策 | 结果 | 含义 |
|---|---|---|
| DP-F018A2A-2 | **A** | `multi_mention` = 1 message + 1 queue entry + N agent targets；不做 N 条消息 |
| DP-F018A2A-3 | **A** | operator target 只通知；不建 parent/TurnExecution；mixed targets 共用 queue entry |
| DP-F018A2A-4 | **A** | cross_post 同 user；target thread active/not deleted/有 projectPath；写 `extra.crossPost` provenance；target agents enabled |
| DP-F018A2A-5 | **A** | v1 删除 `kind`；工具只收 bodyMd/question/context + targets + replyTo + clientMessageId |

- `DP-F018A2A-1`：已完成全量调查，推荐 **A+（统一 `clientMessageId`、删除 `requestId`）**，等 operator 确认（见 §12）。

## 2. Current truth

### 2.1 工具路径

```text
pi worker
  → worker-extension.ts 注册 A2A tool
  → ControlClient.a2aCall()
  → control socket { type:"a2a_call", workerId, token, toolName, input }
  → daemon ControlServer
  → resolveWorkerBinding() 验 token + turnExecution/session/worker
  → A2AToolHandlers
  → message + InvocationQueue.enqueue
```

当前 task-first `a2a/` / `worker-extension.ts` / `auth/*` 是参考实现，不是 F018 契约。

### 2.2 v1 工具面

| 工具 | 行为 | 入队 |
|---|---|---|
| `post_message` | 同 thread 发言，typed targets | 是 |
| `cross_post_message` | 跨 thread 发言，typed targets | 是 |
| `multi_mention` | 2-3 个 agent fan-out，不做聚合回调 | 是 |
| `thread_context` | 只读 thread 窗口 | 否 |

### 2.3 已定边界（不再拍）

- targets 是 `{kind:"agent"|"operator", id}`，不是正文 `@`。
- 正文 `@` 不路由；只有显式 typed target 非法才 reject。
- operator-only 只通知，不创建 parent/TurnExecution。
- `post_message` 拒绝 `threadId`；`cross_post_message` 必须有 `threadId`。
- A2A depth 上限 15；loop guard 在 admission 前判。
- `thread_context` 只读，不 ack delivery cursor，不入队。
- `InvocationQueue.enqueue` 与 message 创建同事务；`queue_admissions` 负责 live row 删除后的重放。

### 2.4 已发现的文档冲突

- `0005 §3.3` 仍把 `post_message` / `cross_post_message` 的 `kind` 写成必填；
  DP-F018A2A-5 推荐 v1 删除。拍板后同步 0005。
- `0005 §3.3` 写 `requestId` scope 为 `(threadId, agentId, requestId)`；
  DP-F018AUTH-3=B 已选 credential-scoped `clientMessageIds`。DP-F018A2A-1
  决定命名后，两处必须统一。
- `0005 §3.3` 的 `multi_mention` 输入是 `question` + `context?`；
  `0010 §3.8` 只写了 targets。v1 固定为 `question`（必填）+ `context?`
  + `targets`（2-3 agents）+ `clientMessageId?`，一条 message + 一个 queue entry。

## 3. DP-F018A2A-1：幂等 key 叫什么

当前设计里同一个概念有两个名字：

- tool input / queue payload：`requestId`
- credential 字段：`clientMessageIds`

| 选项 | 行为 | 价值 | 代价 |
|---|---|---|---|
| **A（推荐）** | 统一叫 `clientMessageId`：tool input、queue payload、credential map key、错误文案全部一致 | 与 Clowder `post_message.clientMessageId` 对齐；一个词一个语义 | 需要把现有 `requestId` 文案/字段统一改名 |
| B | 统一叫 `requestId`：credential 字段改 `requestIds` | 保留 codeteam 现名 | 与 Clowder 工具面不一致；`requestId` 容易被误解为 HTTP request id |
| C | tool 用 `requestId`、credential 用 `clientMessageIds` | 不改现有代码 | 同一个 key 两个名字，长期最容易混 |

**推荐理由**：这是 agent 工具层的“客户端消息幂等键”，Clowder 叫
`clientMessageId`；credential 字段本来就是 `clientMessageIds`。统一后 tool、
queue、credential、错误 taxonomy 只有一个词。

**A+ 补充（2026-11-11 全量调查后）**：不是把所有 ID 都改成一个名字，而是
只统一**客户端幂等键**这一层：

- tool input / queue input / credential map key / 错误文案统一为 `clientMessageId`；
- `clientMessageIds` 是 credential 上的 **claim map**（key 是 `clientMessageId`），
  不是第二个 ID；
- `messageId` / `queueEntryId` / `turnExecutionId` / `invocationId` / `credentialId`
  是 server-generated entity ID，保留原义，不能改成 `clientMessageId`；
- `intentHash` 是 payload fingerprint，不是 ID；保留，用于“同 key 不同 intent”冲突；
- `(sourceRecordId, attempt)` 是 queue admission receipt key，内部使用，不上工具面；
- `idempotencyKey` 只保留给非消息域命令（handoff/approval/budget）；F018 v1 的
  四工具不需要它。

**不拍的后果**：实现会继续在 `requestId` / `clientMessageId` 之间二选一，
测试和文档无法稳定。

## 4. DP-F018A2A-2：`multi_mention` queue 形状（已拍板 A，2026-11-11）

| 选项 | 行为 | 价值 | 代价 |
|---|---|---|---|
| **A（推荐）** | 1 条 message + 1 个 queue entry（targets=N agents）+ N 个 TurnExecution；fan-out，无聚合回调 | 与 F018 “one message + one queue entry + N invocations”一致；credential claim 只记一次 | queue entry 的 targets 多 target 调度；已有 target-level claim 支持 |
| B | N 条 message + N 个 queue entry | 每个 target 独立消息 | 用户会看到 N 条重复正文；与“multi_mention 是一条消息”冲突 |
| C | 1 条 message + N 个 queue entry | 每个 target 独立队列 | queue 行数膨胀；credential claim 需要 N 个 refs；与 A 相比没有明显收益 |

**推荐理由**：F018 已把 `multi_mention` 定义为 fan-out，不是 N 条独立发言；
一条 message + 一个 queue entry 让 queue/read model 只看到一个 source。

**不拍的后果**：`multi_mention` 的实现会在“一条消息”和“N 条消息”之间摆动，
queue admission、message dispatchRefs、UI 都会返工。

## 5. DP-F018A2A-3：operator target 生命周期（已拍板 A，2026-11-11）

| 选项 | 行为 | 价值 | 代价 |
|---|---|---|---|
| **A（推荐）** | operator target 只通知：写 `delivery.operatorNotifiedAt`，在 message `dispatchRefs` 同事务 settle；不建 parent/TurnExecution；mixed targets 与 agent 共用 queue entry | 与“operator 只通知不执行”一致；没有假执行记录 | 需要明确 operator dispatchRef 的 phase/responseMessageId 语义 |
| B | 为 operator 建独立通知行/queue entry | 通知状态更显式 | 多一套行；与 mixed targets 的 queue 事务复杂化 |
| C | 不支持 operator target | 最简单 | 失去 agent→operator 的通知能力；与 F018 目标不符 |

**推荐理由**：operator target 是“可见/通知”，不是 agent 执行；不应该创建
parent/TurnExecution。mixed 场景下 operator 和 agent 共用同一个 queue entry，
但 operator 只 retire + settle dispatchRef。

**不拍的后果**：operator-only 的 queue entry 是否删除、message 的 dispatchRef 怎么结算、
返回结果长什么样都无法定稿。

## 6. DP-F018A2A-4：`cross_post_message` 边界（已拍板 A，2026-11-11）

| 选项 | 行为 | 价值 | 代价 |
|---|---|---|---|
| **A（推荐）** | 同 user；target thread 必须 active/not deleted/有 projectPath；message 写 `extra.crossPost={sourceThreadId, sourceMessageId}`；target agents 必须 enabled | 跨 thread 可达 + 可审计；与 thread access 一致 | admission 多一次 target thread 校验 |
| B | 只查同 user，不查 target thread 状态/projectPath | 实现简单 | 可能投递到 deleted/无 projectPath 的 thread；违反 F018 projectPath 必填 |
| C | 允许跨 user | 更通用 | v1 单 user ownership 不成立；安全边界破裂 |

**推荐理由**：cross-thread 是 v1 能力，但仍然是同 user 的 thread；target thread
的 active/projectPath 是执行前提。`extra.crossPost` 是 Clowder 已有的 provenance 形状。

**不拍的后果**：cross_post 的 access、provenance、deleted/projectPath 负例无法定稿。

**拍板结果：A。** target thread 必须 active/not deleted/有 projectPath；message 写
`extra.crossPost={sourceThreadId, sourceMessageId}`；target agents 必须 enabled；
不同 user、同 thread、soft-deleted、缺 projectPath 都 typed reject。

### 6.1 场景表（给 operator 决策用）

这里的“边界”只决定两件事：**消息能不能落到目标 thread**、**落下后有没有可执行/可审计的前提**。
v1 是单 user，所以 A/B/C 的差别不是“跨用户权限”，而是目标 thread 状态和 provenance：

| 场景 | A（推荐） | B | C |
|---|---|---|---|
| 同 user，目标 thread active + 有 projectPath | 投递 + 唤醒 target + 写 `extra.crossPost` | 同左，但无 provenance | 允许 |
| 同 user，目标 thread soft-deleted | reject `thread_deleted` | 仍投递（消息可能永远无人执行） | 允许 |
| 同 user，目标 thread 缺 projectPath | reject `thread_project_path_required` | 仍投递（target agent 无法启动） | 允许 |
| 目标 agent disabled / 不存在 | reject `agent_disabled` / `agent_not_found` | 同左 | 同左 |
| 不同 user | reject `thread_access_denied`（v1 单 user） | reject（同 user 检查） | 允许 |
| `threadId` 等于 caller thread | reject `use_post_message` | 同左 | 同左 |

**为什么仍推荐 A**：A 不是新安全模型，只是把已有的 thread access 检查 + projectPath
前置到 cross-post admission，并补一个 `extra.crossPost` provenance；B 会把“能写进
thread 但不能执行”的消息留成死信，且下游无法判断 `isCrossThread`。A 的额外成本只有
一个字段和两个已有检查；未来从 A 放宽到 B 只需删检查，从 B 收紧到 A 需要回填 provenance。

## 7. DP-F018A2A-5：`kind` 字段（已拍板 A，2026-11-11）

当前 F018 早期文档的 `post_message` 输入有 `kind`（question/answer/proposal/
finding/status），但 `StoredMessage` 没有 `kind`，且 `extra.kind` 已作为
task-first legacy 删除。

| 选项 | 行为 | 价值 | 代价 |
|---|---|---|---|
| **A（推荐）** | v1 删除 `kind`；工具只收 bodyMd + targets + replyTo + clientMessageId | 与 StoredMessage 对齐；不再把 legacy 分类带进 A2A | UI 失去“讨论类型”提示 |
| B | `kind` 只进 `extra.presentation.kind`，不参与路由/lifecycle | 保留 UI 展示 | 需要定义 presentation schema；工具面多一个字段 |
| C | 保留 required `kind` | 兼容旧工具 | 与 StoredMessage/legacy 清理冲突；`kind` 会继续被误用为路由/生命周期 |

**推荐理由**：F018 已删除 `extra.kind`；如果 UI 需要讨论分类，v2 再以
`extra.presentation.kind` 加回。v1 不让 `kind` 进入消息/session 语义。

**不拍的后果**：`post_message` 的 schema 与 StoredMessage 继续不一致，工具输入
和消息记录会各说一套。

| 事项 | 决定 | 依据 |
|---|---|---|

## 12. 幂等 key 全量调查（2026-11-11）

### 12.1 Clowder 实际有几层

Clowder 不是“只有一个 ID”，而是 **一个客户端幂等名 + 若干内部派生键**：

| 层 | 名称 | 谁生成 | 作用 | 是否客户端可见 |
|---|---|---|---|---|
| tool/message | `clientMessageId` | client | `post_message` / `cross_post_message` / capability-evolution 等工具的 retry 幂等 | 是 |
| tool/group | `idempotencyKey` | client | `multi_mention` group、action successor、command 的 retry 幂等 | 是（不同工具） |
| message store | `message.idempotencyKey` | server 派生 | 如 `callback:post:<catId>:<sha256(clientMessageId)>`、`multi-mention-source:<requestId>`、`message-lifecycle-response:<invocationId>` | 否 |
| queue | `sourceId` / `queueEntryId` / attempt | server | queue admission 与 target-level claim | 否 |
| auth | `InvocationRegistry.clientMessageIds` | — | 参考仓里是 `Set<string>`，**没有 route 调用点**，不是 live 机制 | 否 |

结论：Clowder 普通消息工具确实以 `clientMessageId` 为主；`idempotencyKey` 留给
group/action/command。把两者混成一个名字会丢失“消息幂等 vs 领域命令幂等”的边界。

### 12.2 codeteam 现有名字的分类

| 名字 | 类别 | 处置 |
|---|---|---|
| `requestId` | A2A tool 客户端幂等键（当前） | **删除**，统一为 `clientMessageId` |
| `clientMessageIds` | credential 上的 claim map（key 是 `clientMessageId`） | **保留**；不是第二个 ID |
| `a2a_requests.request_id` | 旧 task-first ledger | legacy 只读；v1 不写 |
| `idempotencyKey` | handoff/approval/budget 等领域命令键 | 保留给非消息域；F018 四工具不用 |
| `(sourceRecordId, attempt)` | queue admission receipt key | 保留；内部两层幂等之一 |
| `intentHash` | payload fingerprint（冲突检测） | 保留；不是 ID |
| `messageId` / `queueEntryId` / `credentialId` / `turnExecutionId` / `invocationId` / `attemptId` / `claimId` | server-generated entity / lease ID | 保留；不能改名成幂等键 |

### 12.3 推荐模型：一个客户端 key，三层内部账

```text
clientMessageId                       // 唯一客户端幂等 key；四工具统一
  └─ credential.clientMessageIds      // claim map: key -> {intentHash, messageId, queueEntryId}
       ├─ intentHash                  // 同 key 不同 intent -> client_message_conflict
       ├─ messageId                   // durable message identity（server）
       └─ queueEntryId                // durable queue identity（server；可能已被删除）

(sourceRecordId, attempt)             // queue admission receipt；row 删除后仍可 replay
  └─ queue_admissions.fingerprint     // immutable admission fields

messageId / queueEntryId / turnExecutionId / invocationId / credentialId
                                      // entity IDs；不是幂等 key
```

**为什么不把所有 ID 合成一个**：

- 客户端 key 必须 retry-stable，且不能由 server 生成；entity ID 必须 server 生成，
  不能由 client 指定。两者生命周期和信任边界不同。
- queue row 会删除；客户端 key 可能随 credential tombstone 回收；queue receipt 需要
  独立 durable key 才能覆盖“row 删除后重放”。
- `intentHash` 不是 key，是“同 key 是否同 payload”的判据；没有它无法区分 replay/conflict。

**v1 落地规则**：

1. 四工具 wire 只暴露 `clientMessageId`；不暴露 `requestId`、`sourceRecordId`、`attempt`。
2. `clientMessageIds` 保持 map；建议类型别名 `ClientMessageClaims`，字段名不改，避免新增名字。
3. `clientMessageId` 可选；pi extension 对每次 mutating tool call 生成一次并在 transport
   retry 中复用同一个值。缺省时是 at-least-once。
4. 同 `clientMessageId` + 同 `intentHash` → `replayed`；不同 → `client_message_conflict`。
5. `queue_admissions` 冲突 → `queue_admission_conflict`；同一 source+target 已 queued/running
   → `a2a_duplicate_delivery`。
6. `a2a_requests` 标 legacy；不迁移旧 `request_id`，只保留历史只读。
7. `multi_mention` 的 `clientMessageId` 是 codeteam 有意统一；Clowder 用 `idempotencyKey`，
   不宣称逐字段对齐。
