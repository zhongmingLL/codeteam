# DP-MERGE-2: W0–W4 dogfood merge execution path

## 0.1 大白话

W0–W4 是 codeteam 的第一段建设期；**dogfood** 是拿 codeteam 自己跑 2–4 个真实小任务，走完 implement → review → verify → merge。

`DP-MERGE-1=D` 已经定了最终谁执行 merge：**daemon 的 merge service，不是 operator**。

但 W0–W4 时 merge service 可能还没做出来。`DP-MERGE-2` 只问这 2–4 个 dogfood 任务的 merge：

| 选项 | 大白话 |
|---|---|
| A（D-first） | 先把 merge service 做出来，再跑 dogfood；慢一点，但一开始就是最终形态，你不用按 merge |
| B（A-interim） | 先由你手动 merge，文档标“临时 A”，dogfood 先跑起来；快一点，但你要按 2–4 次 merge |
| C | 等 merge service 完全做好再 dogfood；不推荐 |

**它不影响 `DP-MERGE-1=D` 的目标契约。** D 仍然冻结；B 只是早期试跑的临时执行方式。

> **Operator 决定（2026-10-25）：A（D-first）。** W0–W4 dogfood 前先落 merge service；不做 A-interim。

## 0. 一句话

`DP-MERGE-1=D` 目标契约已冻结，三猫 review 也收敛了 D 的六个契约；**只剩一个排期/operator 负担取舍**：W0–W4 dogfood 是先把 D 的 merge service（`service:merge-owner` + per-merge credential + daemon 强制 E1–E5）做出来再跑，还是先用 A（operator 手工执行）作明确标注的临时偏差、D 在 W7/W8 落地。

## 1. 为什么现在要拍

- W0–W4 dogfood 必须跑到 merge 完成；没有 merge 执行路径，dogfood 无法验收。
- D 的三猫冻结方案要求 daemon service principal + per-merge short-TTL credential + 服务端 E1–E5 核验；这是一块真实的安全/运行时 scope，不是一句配置。
- 如果先做 D，dogfood 会多一段实现和安全验证；如果先用 A，operator 会成为 W0–W4 的每 PR merge 按钮，并且 A/D 双语义窗口期变长。
- 这不是技术 A/B：两条路都能实现 D；取舍是 **dogfood 速度 vs operator 负担 + A/D 漂移风险**。

## 2. 选项

| 选项 | 行为 | 价值 | 代价 |
|---|---|---|---|
| **A（D-first）** | W0–W4 前先落 `service:merge-owner` + per-merge credential + daemon E1–E5 核验；dogfood 直接用 D | 不在 dogfood 期引入 operator merge 按钮；A/D 无双语义；能真实测 D 的 latency/failure/unknown | W0–W4 多一段安全/运行时实现；首次 dogfood 可能后移 |
| **B（A interim, D at W7/W8）** | W0–W4 由 operator 执行 routine merge；在文档/指标里显式标注 A 临时偏差；D 六个契约保持冻结，W7/W8 实现 | dogfood 最快启动；operator 亲历 merge 摩擦；不需要提前做 credential | operator 成每 PR 瓶颈；A 习惯可能泄漏进 D；需要明确的退出/截止条件 |
| **C（defer dogfood merge）** | 等 D merge service 完全就绪再跑 W0–W4 | 最干净 | 阻塞 W0–W4；不建议 |

## 3. Operator 决定与解释

**决定：A（D-first）。** W0–W4 dogfood 前先落 `service:merge-owner` + per-merge credential + daemon E1–E5 核验；dogfood 的 merge 由 merge service 执行，operator 不做 routine merge 按钮。

**落地补充（避免被 W8 阻塞）**：W0–W4 的 dogfood 是隔离 worktree/本地分支，不 push，因此 merge service 先接 **local `MergeExecutor` adapter**（本地 git merge + branch/receipt reconciliation）；W8 再接 **GitHub adapter**（PR merge API + reconciliation）。两者共用同一 `merges` receipt、`service:merge-owner`、E1–E5 核验和 `merge:execute` 契约；adapter 只替换执行通道，不改变 D 契约。

**先看你的目标：**

- **想尽快把 dogfood 跑起来**：**B**。W0–W4 只有 2–4 个任务，你最多手动合 2–4 次；先把闭环跑通，拿到真实摩擦数据，D 在 W7/W8 前落地。
- **想一开始就不当 merge 按钮 / 尽早验证 D**：**A**。三猫的 D 方案已经做到零-secret 兼容，P1-1 的 daemon E1–E5 是承重墙；代价是 dogfood 前多一段安全/运行时实现。

~~我的倾向：如果 W0–W4 dogfood 确实只有 2–4 个任务，B 更划算……~~ **此倾向已被 operator 的 A 决定覆盖。** 记录 A 的理由：早期就验证 D、避免 A/D 双语义；B 保留为历史备选。

**如果选 B，必须满足**：

- 文档、指标、W7 UI 都显式标 `A-interim`，不得写成 clowder SOP；
- 设定退出条件（例如 W4 结束或 W7a 开始前），到期必须切 D；
- 记录 `operator_hard_gate_wait` 与 `routine_merge_operator_touch_total`，把 A 的代价量化，作为切 D 的证据。

**C 不推荐**：阻塞 W0–W4，且不会降低 D 的总实现成本。

## 4. 选 A/B 分别改什么

| 选择 | W0–W4 scope | 指标 | skill/文档 | 退出条件 |
|---|---|---|---|---|
| A | 增加 merge service + credential + E1–E5 核验 | `merge_owner_latency` / `failure` / `unknown` | merge-gate 按 D 重写 | 无 A 窗口 |
| B | 不增加 merge service；operator CLI 执行 | `operator_hard_gate_wait` + `routine_merge_operator_touch_total` | 同一套文档标 `A-interim` | W4 结束或 W7a 前必须切 D |

## 5. 决定后的落地

- W0–W4 增加 merge service：`merges` 执行记录 + `service:merge-owner` + `merge:execute` + 服务端 E1–E5 + local `MergeExecutor` adapter。
- W8 增加 GitHub adapter；契约不变。
- dogfood 指标记 `merge_owner_latency` / `failure` / `unknown`；不记录 routine operator merge touch（应为 0）。
- `merge-gate` skill 按 D 重写；operator 硬门清单 `MS-MERGE-8` 必须逐字在场。
- B（A-interim）不再作为 W0–W4 执行路径；仅在 D service 无法在 W0–W4 落地时，单独向 operator 申请重新拍板。

## 6. 决定记录

`DP-MERGE-2=A`（2026-10-25）。C（整体后移 dogfood）不采用；B（A-interim）不采用。
